背景

database_masking は、実データを外部分析基盤に渡す前に、顧客環境内で安全に前処理するためのローカル実行ツールです。ツールが担う範囲は、不要項目削除から検出漏れチェックまでです。

外部分析基盤への投入、人間によるレビュー、持ち出し承認はツール外の工程です。ツールは、承認前に「どのカラムに何をするか」を明示し、未定義カラムをそのまま持ち出さない設計を採ります。

全体アーキテクチャ

mask は入力データと policy.yaml を読み込み、カラムポリシーを適用します。verify はマスク済みデータへ同じ検出器を再適用し、残存PII候補をCSVまたはJSONで出力します。

領域責務主な実装
設定ポリシー読込、カラム網羅性、命名規約を検証するsrc/config.py
入出力CSV、Excel、SQLiteを読み書きするsrc/io/

ポリシー

policy.yaml は入力カラムに対する処理を明示します。入力データに存在するのにポリシーへ定義されていないカラムがある場合、mask はエラーで停止します。

action意味用途
dropカラムごと削除メール、電話番号など不要な項目
pseudonymizeセル値全体を仮名化氏名、顧客ID、住所など
keepそのまま維持年齢、商品カテゴリなど
freetextセル内の該当箇所だけ仮名化問い合わせ本文など
columns:
  customer_id: {action: pseudonymize, entity_type: CUSTOMER_ID}
  name:        {action: pseudonymize, entity_type: PERSON}
  email:       {action: drop}
  inquiry:     {action: freetext}

custom_patterns:
  - entity_type: CUSTOMER_CODE
    regex: 'CUST-\d{6}'

spacy_model: ja_core_news_sm

検出と仮名化

freetext カラムには、RegexレコグナイザとPresidio NERを重ねます。複数レイヤーの検出が重なる場合は、スコア降順、同点ならスパン長の降順で非重複の検出結果を選びます。

仮名化はHMAC-SHA256ベースで、{entity_type}_{8桁16進数} の形式を返します。元の値と仮名の対応表は保存せず、saltのみを .secrets/salt.key に保持します。

verifyの仕組み

verify は mask と同じポリシーから同じ検出器を再構築し、マスク済みデータに残ったPII候補を出力します。レポートには検出テキストの原文が含まれるため、外部へ渡さない運用が前提です。 

row_index,column,entity_type,detected_text,score
128,inquiry,PERSON,"田中様",0.85

仮名化トークン自体の誤検出は PSEUDONYM_TOKEN_PATTERN で除外します。ただし、同じ検出器を再利用するため、モデル起因の検出漏れは verify にも現れません。

CLIと運用

python -m database_masking mask \
  --input sample_data/customer_raw_sample.csv \
  --policy config/policy.example.yaml \
  --output output/masked.csv \
  --salt-file .secrets/salt.key

python -m database_masking verify \
  --input output/masked.csv \
  --policy config/policy.example.yaml \
  --output output/verify_report.csv
  • SQLite入力では --input-table、SQLite出力では --output-table が必要です。
  • PostgreSQLやMySQLなどへのライブDB接続はスコープ外です。
  • ja_core_news_sm の既知の検出漏れは、test_known_limitations.py に回帰記録されています。
