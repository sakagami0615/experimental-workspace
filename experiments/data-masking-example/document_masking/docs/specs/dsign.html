背景

document_masking は、問い合わせメモや議事録のような自由記述ファイルを、顧客の閉域環境内でマスキングするための独立ツールです。外部APIや外部通信に依存せず、データ持ち出し前の前処理として実行されます。

表形式データ向けの database_masking とは分離されています。自由記述文書には「氏名カラム」「電話番号カラム」のような構造がないため、ファイル全体を1つのテキストとして扱い、検出器を一様に適用します。

表形式データ

カラムごとの意味があり、drop や pseudonymize といったポリシーを列単位で適用できます。

自由記述文書

PII候補の位置や個数は文書ごとに異なるため、文書全体を検出対象にします。

全体アーキテクチャ

CLIは mask と verify に分かれます。どちらも document_masking.detectors.analyzer.build_analyzer() で同じ検出器を作り、RegexとPresidio NERを同じ条件で利用します。

段階役割主な実装
読み込みファイル全体をUTF-8テキストとして読むmasking/masker.py
検出Regex、NERでPII候補を抽出するdetectors/analyzer.py
置換重複検出を解消し、末尾側から仮名化するmasking/pseudonymizer.py
検証マスク済み文書を再スキャンして候補を報告するverify/scanner.py

検出レイヤー

検出は多層構成です。Regexレコグナイザは日本の電話番号や郵便番号、任意のカスタムパターンを拾います。Presidio NERはspaCy日本語モデルで人名、地名、組織、日時などを検出します。

Regex

PHONE_NUMBER、JP_POSTAL_CODE、顧客固有の正規表現を検出します。

NER

ja_core_news_sm を既定に、Presidio経由で自然言語中の固有表現を扱います。

重複解消

複数レイヤーの検出が重なる場合は、スコアとスパン長を基準に非重複の候補を選びます。

仮名化と検証

仮名化はHMAC-SHA256ベースの決定的アルゴリズムです。同じsalt、同じ正規化入力、同じ entity_type なら常に同じトークンになり、元の値との対応表は保存しません。 

def pseudonymize(value: str, entity_type: str, salt: bytes) -> str:
    normalized = normalize(value)
    digest = hmac.new(salt, normalized.encode("utf-8"), hashlib.sha256).hexdigest()
    return f"{entity_type}_{digest[:8]}"

verify では、PERSON_a3f9c2e1 のような仮名化トークン自身を誤ってPII候補として報告しないよう、PSEUDONYM_TOKEN_PATTERN と重なる検出結果を除外します。

CLIと運用

python -m document_masking mask \
  --input sample_data/sample_inquiry.txt \
  --output output/masked.txt \
  --salt-file .secrets/salt.key \
  --spacy-model ja_core_news_sm

python -m document_masking verify \
  --input output/masked.txt \
  --output output/verify_report.json

verify の終了コードは、候補がなければ 0、1件でもあれば 1 です。CIなどの自動チェックに組み込めますが、最終判断はレポートとマスク済みファイルの人間レビューで行います。

制限とスコープ外

既定の ja_core_news_sm では、日本語人名の一部が検出されずに残る可能性があります。verify も同じ検出器を使うため、同じ盲点を共有します。本番運用では ja_core_news_lg の利用と、目視確認を推奨します。

  • WordやPowerPointなどのOfficeファイル形式は対象外です。
  • 自由記述文書向けのため、カラム単位の policy.yaml は持ちません。
  • database_masking との共通ライブラリ化はせず、各ツール内で独立して保守します。
